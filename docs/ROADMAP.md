# Agent Web 改进路线图

本文记录 Agent Web 下一阶段的改进范围与实施顺序。目标是在不改变项目“单机优先、轻量部署、管理多种原生 Coding Agent”的定位前提下，提高运行可靠性和任务管理能力。

## 目标与原则

- 保留 Codex、Claude、Gemini、OpenCode、Pi、Qwen 的原生 CLI、原生 Session 和原生配置。
- 不持久化完整聊天正文和完整 Agent 事件流；优先从 Agent 原生 Session/Transcript 恢复内容。
- 不引入不必要的通用 Agent Runtime、模型发现框架或复杂微服务。
- 默认继续使用用户 HOME 作为 Workspace；安全隔离作为可选能力逐步增加。
- 先修复可靠性和明确的功能缺口，再扩展任务编排和外部集成。
- 每个阶段独立实现、测试和提交，避免一次性大规模重构。

## 阶段 0：建立基线

- [x] 静态梳理 main 分支构建、测试、部署入口和 CI 配置。
- [ ] 实际执行并确认构建、测试和 Docker 部署流程（等待自动 CI 结果）。
- [ ] 梳理六种 Agent 的启动、继续会话、停止、异常退出和恢复行为。
- [ ] 为各 Agent 建立统一的手工/自动化兼容性测试矩阵。
- [x] 记录当前已知问题和可复现步骤（见 [BASELINE.md](BASELINE.md)）。

已发现：原 CI 仅支持手动触发，现已改为 main push / pull request 自动触发，并补入前端纯逻辑检查和 Rust 格式检查；Cron 当前只接受 UTC 时区；跨 Worker Event Relay 为 best-effort；六种真实 Agent CLI 的生命周期集成测试尚未形成矩阵。

验收标准：
- 能明确区分已实现、已测试和未经验证的能力。
- 六种 Agent 的核心生命周期都有对应测试或明确的已知限制。

## 阶段 1：运行可靠性（最高优先级）

### 1.1 Session 与执行生命周期

- [ ] 检查服务重启后 Session Runtime 状态恢复。
- [ ] 检查 Agent 子进程异常退出、用户中断和服务关闭时的状态收敛。
- [ ] 验证执行租约过期、并发 Worker 抢占和重复执行防护。
- [ ] 统一区分运行中、成功、失败、中断和等待输入等状态，避免 UI 与实际进程状态不一致。
- [ ] 为原生 Session 丢失、不可恢复等情况提供明确错误信息和恢复建议。

### 1.2 WebSocket 与状态恢复

- [x] WebSocket 心跳、断线指数退避重连，以及重连后重新获取 Session/Execution HTTP 快照（前端已有实现）。
- [ ] 从六种 Agent 的原生 Transcript 恢复对话；Pi、Codex、Claude 已接入读取，Gemini、OpenCode、Qwen 尚未支持。
- [ ] 为关键生命周期事件建立轻量元数据或状态快照，不持久化聊天正文。
- [x] broadcast Lagged 时发送 resync_required 并关闭连接，触发现有重连/快照恢复流程。
- [ ] 处理跨 Worker Relay 队列丢失事件时的端到端 resync 通知。
- [ ] 增加断线重连、页面刷新、服务重启和慢客户端测试。

约束：不将完整消息正文、Thinking 和 Tool 事件流写入 SQLite。优先读取各 Agent 原生 Session 文件或官方只读接口；不要为恢复历史消息而重新建立 Agent Web 自己的聊天记录库。

### 1.3 定时任务调度

- [x] 实现任务配置的 IANA 时区支持（例如 Asia/Shanghai；待 CI 验证）。
- [x] 引入 chrono-tz 处理 IANA 时区；保留现有五段 Cron 字段解析语义（待 CI 验证）。
- [ ] 验证错过执行时间后的补跑策略。
- [ ] 验证多实例竞争、租约过期恢复、长任务重叠和任务删除时的执行行为。
- [x] 增加夏令时跳时/重复时间测试；时区变更场景仍需补充。

实现进度：IANA 时区计算、API 校验、前端时区输入和 DST 测试已提交；等待自动 CI 验证后再关闭本项。

验收标准：
- 调度时间按任务配置时区计算。
- 同一个调度点不会被多个 Worker 重复领取执行。
- 服务重启后的补跑行为符合既定策略，并有测试覆盖。

## 阶段 2：安全边界与运行可观测性

### 2.1 安全边界

- [ ] 审核 Workspace、文件浏览、文件预览、上传和 Git 操作的路径边界。
- [ ] 审核 Terminal 与 Agent 子进程的权限继承和进程清理。
- [ ] 明确 HOME 共享 Workspace 的风险和提示。
- [ ] 设计可选的项目目录限制、独立 Worktree 和受限工具模式。
- [ ] 增加针对路径穿越、符号链接、并发文件操作和权限错误的测试。

原则：不改变默认 HOME Workspace 行为；可选隔离模式不得暗中改变现有用户的目录语义。

### 2.2 运行状态与诊断

- [ ] 区分后端存活检查与 Agent 运行环境健康检查。
- [ ] 展示 Agent CLI 是否安装、版本和可执行路径。
- [ ] 展示当前运行中的 Session、执行时长和最近错误。
- [ ] 增加失败原因、退出码和必要的诊断信息。
- [ ] 评估 Token/费用统计的数据来源和准确性；没有可靠来源时不展示推测值。

验收标准：
- 用户能判断后端是否正常、Agent 是否可用、Session 是否正在执行以及失败原因。
- 不收集或持久化不必要的敏感对话内容。

## 阶段 3：Agent 能力一致性与使用体验

- [ ] 梳理六种 Agent 的能力差异，明确哪些能力是通用操作、哪些必须保留 Agent-specific 实现。
- [ ] 完善原生 Transcript 展示，包括 Thinking、Tool 调用、结果、错误和文件变化（以各 Agent 实际提供的数据为准）。
- [ ] 验证模型切换、Thinking Level、工具权限配置是否真正作用于对应 CLI。
- [ ] 完善 Agent 安装、更新、卸载和版本检测。
- [ ] 检查 MCP 管理的连接测试、认证状态和错误提示。
- [ ] 评估 Skills/Plugins 管理；优先读取和调用 Agent 原生机制，不强行统一不同 Agent 的配置格式。

验收标准：
- UI 对各 Agent 的能力差异有明确反馈，不把不支持的操作伪装成通用能力。
- 核心操作具有一致的交互语义和可理解的错误提示。

## 阶段 4：Git 工作流与任务模型

### 4.1 Git 工作流

- [ ] 完善分支、状态、提交历史和 Diff 展示。
- [ ] 支持从 Session/任务创建独立 Git Worktree。
- [ ] 支持查看修改、提交变更和清理 Worktree。
- [ ] 明确多个 Session 共享目录时的冲突风险。
- [ ] PR 创建和状态跟踪作为后续可选集成。

### 4.2 轻量 Task 模型

引入 Task，但不一开始照搬复杂 Ticket/Assignment 系统。

初期建议关系：

```text
Task
 ├── Execution 1
 │    └── Agent Session
 ├── Execution 2 (retry)
 │    └── Agent Session
 └── Workspace / Worktree
```

- [ ] 定义 Task、Execution 与 Agent Session 的边界。
- [ ] Task 记录目标、状态、Agent、Workspace 和关联 Session。
- [ ] Execution 记录每次执行的开始、结束、结果和错误摘要。
- [ ] 支持失败重试和重新执行，并明确是否复用原生 Session。
- [ ] 保持聊天正文和完整事件流由 Agent 原生 Session 管理。

验收标准：
- 一个 Task 可以有多次 Execution。
- Task 不依赖某一个固定 Agent Session 才能存在。
- 不破坏现有 Session 的创建、恢复和删除行为。

## 阶段 5：自动化与外部事件

在 Task 模型稳定后再考虑：

- [ ] Webhook 触发 Task。
- [ ] 通过 API 创建、查询和取消 Task。
- [ ] GitHub Issue/PR 事件集成。
- [ ] 任务执行前的规则判断和人工确认。
- [ ] 执行完成后发送通知。
- [ ] 评估外部 Worker/多机器执行；只有单机能力遇到明确瓶颈时再实施。

## 暂不纳入当前范围

以下能力暂不作为近期目标：

- 完整多租户 RBAC 和团队协作平台。
- 通用多 Agent 自主协商/群体编排。
- 强制引入独立调度服务、消息队列或微服务。
- 默认将所有 Session 改成独立容器或独立目录。
- 为了统一接口而重写各 Agent 原生配置和 Session 机制。
- 在没有可靠数据源的情况下展示 Token/费用统计。

## 实施约定

1. 按阶段顺序推进，优先处理阶段 0 和阶段 1。
2. 每次只聚焦一个可验证的改动单元。
3. 修改前检查当前 main 分支实现，避免重复开发。
4. 每个改动完成后运行相关测试、构建和必要的手工验证。
5. 使用中文 Git commit message。
6. 每个阶段完成后更新本文勾选状态和已知限制。
